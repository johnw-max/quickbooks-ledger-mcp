# Connector profile: QuickBooks formal ledger

## Role

- `ledger_sor`

Map only mounted tools after the platform verifies the connection, Realm binding, scope, permission, object support, and current write gate. QuickBooks 0.6.0 runs in Accounting Case mode: the server always constructs the Accounting Case service, so exactly this 18-tool surface is mounted and the legacy prepare tools below are never mounted alongside it.

| Tool | Capability ID | Supported object types | Control requirement |
|---|---|---|---|
| `quickbooks_connection_status` | `connector.connection.status.read` | `connector_control_plane`: connection health and bound-connection display | `quickbooks.read`; server-resolved connection; never target proof by itself |
| `quickbooks_resolve_target`, `quickbooks_get_company` | `ledger.target.resolve` | QuickBooks Company (target session) | Bound Realm, `quickbooks.read`; call in that order — `quickbooks_resolve_target` issues the short-lived `target_session_ref`, `quickbooks_get_company` reads and confirms the full bound Company object (name, currency) that the resolve envelope requires |
| `quickbooks_list_accounts` | `ledger.reference.accounts.read` | Account | Bound Realm, `quickbooks.read`, valid `target_session_ref` |
| `quickbooks_list_tax_codes` | `ledger.reference.tax.read` | TaxCode | Bound Realm, `quickbooks.read`, valid `target_session_ref` |
| `quickbooks_search_vendors`, `quickbooks_search_customers` | `ledger.reference.counterparty.read` | Vendor, Customer | Bound Realm, `quickbooks.read`, valid `target_session_ref`; non-empty name/email query, `limit` 1-100; bounded `searchWindow` evidence, not an unfiltered list-all |
| `quickbooks_list_items` | `ledger.reference.item.read` | Item | Bound Realm, `quickbooks.read`, valid `target_session_ref`; reference support only |
| `quickbooks_list_bills`, `quickbooks_list_transactions` | `ledger.transaction.search` | Bill and supported transactions (invoices, payments, purchases, bill payments, journal entries, credits, sales receipts) | Bound Realm, `quickbooks.read`, valid `target_session_ref`; `quickbooks_list_transactions` `page_size` is capped at 1-50, follow `hasNextPage` instead of raising it |
| `quickbooks_get_bill`, `quickbooks_get_transaction` | `ledger.object.read_exact` | Exact Bill or supported transaction | Bound Realm, `quickbooks.read`, valid `target_session_ref`, exact provider object ID |
| `quickbooks_run_report` | `ledger.report.read` | Supported report (Profit and Loss, Balance Sheet, cash flow, aging, balances, expenses, general ledger, trial balance) | Bound Realm, `quickbooks.read`, valid `target_session_ref`; `as_of_date` or a start/end period, never both |
| `quickbooks_get_trial_balance` | `ledger.report.trial_balance.read` | Trial Balance | Bound Realm, `quickbooks.read`, valid `target_session_ref`; exact Realm/date/basis |
| `quickbooks_get_write_capabilities` | `connector.capability.describe` | Static catalog: all 71 tracked Intuit write operations (25 create, 26 update, 20 delete) plus zCloak risk, execution-mode, and draft-availability policy | `quickbooks.read`; no `target_session_ref` — not bound to a Realm; catalog/policy information only, never proof that a listed capability is enabled for this installation |
| `quickbooks_prepare_accounting_case` | `ledger.accounting_case.prepare` | Business-shaped source units compiled to a typed Case; released routes are Customer, Vendor, Account, Item, Invoice, Bill, CreditMemo, VendorCredit, JournalEntry, Purchase, SalesReceipt, and Attachable create; a residual Case may hold only `UNSUPPORTED_EVENT`, `EVIDENCE`, or `CONTROL_FINDING` facts | `quickbooks.mutation.prepare`, bound Realm, valid `target_session_ref`; the Agent submits business facts only, never fact ids, lineage, or Provider ids; the server verifies coverage, recomputes totals, resolves QuickBooks references, and stores immutable canonical operations; no provider write |
| `quickbooks_execute_accounting_case` | `ledger.accounting_case.execute` | Current Case version; Customer, Vendor, Account, Item, Invoice, Bill, CreditMemo, VendorCredit, JournalEntry, Purchase, SalesReceipt, Attachable CREATE operations only | `quickbooks.mutation.execute` transport scope plus an active standing delegation for the exact action and Realm, and the write kill switch enabled; runtime revalidates exact target/scope, deterministic validation, durable preflight, idempotency, one-shot provider permit, provider receipt and exact read-back; no confirmation phrase or per-item approval |
| `quickbooks_get_accounting_case_status` | `ledger.accounting_case.status.read` | Exact durable Case version and recovery state | Bound Realm, `quickbooks.read`, same bound target, or renewed same-Company read-only recovery; never creates or retries a provider write |

`quickbooks_connection_status` is connection health, not a verified ledger target. `quickbooks_get_write_capabilities` is a static catalog and risk-policy read; it takes no `target_session_ref`, is not bound to a Realm, and does not by itself certify that any listed capability is enabled for this installation. Read its fields in route order. `runtime.agentFacingMode` is `ACCOUNTING_CASE` here, so the fields that govern this Agent are `accountingCaseReleased` and `runtimeExecutionEnabled`. The per-capability `agentMayExecute` and `executionMode` fields describe the **legacy generic-mutation route only**, which is not mounted: they report `false` / `HUMAN_REVIEW` for Invoice, Bill, CreditMemo, VendorCredit, Purchase, SalesReceipt, Account and Item creates, and `false` / `CRITICAL` / `RESTRICTED_HUMAN_REVIEW` for JournalEntry create, even though all nine are released to this Agent through `quickbooks_execute_accounting_case`. Do not read `agentMayExecute: false` as a refusal to prepare or execute a released Accounting Case operation. `quickbooks_prepare_supplier_bill` and `quickbooks_hash_source_document` are the legacy prepare surface: the server registers them only when the Accounting Case service is absent, and the deployed 0.6.0 runtime always constructs that service, so these two tools are never mounted here and must not be presented as available. `ledger.transaction.native.execute` is reached only through `quickbooks_execute_accounting_case`, and only for the twelve released Accounting Case actions above; no tool exposes a generic native-execute for the remaining catalogued write operations.

For a new conversation, call `quickbooks_resolve_target` as a separate first ledger step once `quickbooks_connection_status` reports a connection, then call `quickbooks_get_company` before any other QuickBooks ledger tool. Do not call either in parallel with reference, search, transaction, report, Trial Balance, or Accounting Case tools. Re-resolve after `target_session_ref` expiry or any Company reconnect/switch. Call `quickbooks_connection_status` again only when target resolution reports no connection or the user explicitly asks to replace the current Company.

## Provider semantics

- Prefer native Customer, Vendor, Account, Item, Invoice, Bill, Credit Memo, Vendor Credit, Purchase, Sales Receipt, Journal Entry, and source-attachment creates for routine activity, but release only the twelve routes the current Case compiler implements (`customer.create_basic`, `vendor.create_basic`, `account.create`, `item.create`, `invoice.create`, `bill.create`, `credit_memo.create`, `vendor_credit.create`, `journal_entry.create`, `purchase.create`, `sales_receipt.create`, `attachment.create`). The boundary is money movement, not difficulty: anything that records the books is in, anything that moves or settles money is deliberately out. Payment, BillPayment, customer prepayment, FX settlement, delete/void, CompanyInfo changes, general updates, and arbitrary provider-shaped payloads remain explicitly unsupported, and the `UNSUPPORTED_EVENT` types are now exactly `PAYMENT`, `BILL_PAYMENT`, `PREPAYMENT`, `OPENING_BALANCE`, and `FX_SETTLEMENT`. `BANK_FEE` and `EXPENSE_CLAIM` were removed: a bank charge is now a Purchase against the bank account, and an expense claim is a Purchase when the company card paid it or a journal entry crediting the employee payable when it did not. `FOREIGN_CURRENCY_BILL` was removed too, on evidence rather than on the code path existing: Bill 154 / `MBC-2026-0820`, S$1,635.00 at 0.783503, posted to the real Sandbox Company on 2026-08-20 with sent payload and exact read-back identical field for field and the provider write count moving by exactly one. A foreign-currency bill is now an ordinary document fact with `exchange_rate`; never file one as an unsupported residual. `OPENING_BALANCE` stays because only half of it is reachable — a plain opening trial balance is a journal entry, but opening AR/AP aging needs a per-customer or per-vendor ledger line that this release cannot carry. `FX_SETTLEMENT` stays because it is the gain or loss realised *by* a settlement, and settlement is out of scope; month-end revaluation is not that, and is an ordinary journal entry.
- A `JOURNAL_ENTRY` fact is the month-end route: accrual, reclassification, depreciation, correction. It has no counterparty and no document total; it has at least two lines, each with `posting_type` `DEBIT` or `CREDIT`, an `account_name` that must match the chart of accounts exactly, and a positive `amount`, plus a `declared_total` that total debits and total credits must each equal exactly. Which account carries the debit and which the credit is your judgment and is never second-guessed; that the two sides add up is arithmetic and is enforced with no tolerance, so an unbalanced entry comes back `BLOCKED_VALIDATION` with `JOURNAL_ENTRY_DEBITS_DO_NOT_EQUAL_CREDITS` or `JOURNAL_TOTAL_DOES_NOT_MATCH_DECLARED_TOTAL` and is fixed by restating the facts. Read account names from `quickbooks_list_accounts`; an absent name is `REFERENCE_NOT_FOUND` and a name held by two active accounts is `REFERENCE_AMBIGUOUS`, and neither is ever guessed past. A journal line against an Accounts Receivable or Accounts Payable account is refused before dispatch with `JOURNAL_LINE_ACCOUNT_REQUIRES_COUNTERPARTY`: QuickBooks needs a customer or vendor on that line and this release carries no such field, so post the receivable or payable side as an Invoice, Bill, CreditMemo or VendorCredit and keep the journal entry to the other accounts.
- A `PURCHASE` document is a cash, cheque, or card expense that has **already** been paid — it records an outflow, it never initiates one. Because of that it is the only document type that also names `payment_account_name` (the exact bank or credit card account the money left from, resolved against the chart of accounts the same way any other account name is) and `payment_type` (`CASH`, `CHECK`, or `CREDIT_CARD`). Both are required on a purchase and refused on any other document type. Naming an expense account as the money source comes back `PAYMENT_ACCOUNT_IS_NOT_A_MONEY_ACCOUNT`. The payee is a Vendor and is staged like any other contact; QuickBooks records it on the Purchase's `EntityRef`. A Purchase carries no due date. Refund purchases (QuickBooks' `Credit` flag) are **not** released: a supplier refund on the accounts-payable side is a Vendor Credit, and a refund straight back to a card has no released route in this version.
- A `SALES_RECEIPT` document is a cash sale — money already received, recorded, never initiated. It is an ordinary sales document in every other respect: a Customer counterparty, `ITEM` coding on every line, no due date. Like a Purchase it also names `payment_account_name`, but here it is the account the money **landed in** — the bank account, or `Undeposited Funds`, which QuickBooks holds as an Other Current Asset and which is its own default for a receipt not yet banked. Those two account kinds are what a sales receipt accepts; anything else comes back `PAYMENT_ACCOUNT_IS_NOT_A_MONEY_ACCOUNT` naming the type it found. A sales receipt never carries `payment_type`: QuickBooks records a receipt's tender through a `PaymentMethodRef` this release does not carry, and sending `payment_type` on anything but a Purchase is refused at the intake boundary.
- `ACCOUNT` and `ITEM` facts add master data mid-close, so a missing expense account or an unbilled service is not a reason to leave the product. An account names `name`, `account_type` (QuickBooks' own AccountType vocabulary, exactly as `quickbooks_list_accounts` shows it), and optionally `parent_account_name` for a sub-account. An item names `name`, `item_type` (`SERVICE` or `NON_INVENTORY` — inventory items need an asset account, an opening quantity and a start date this release does not carry), `income_account_name`, and optionally `expense_account_name` for the purchase side. Both resolve and de-duplicate exactly as a contact does: an account or item that already exists comes back `EVIDENCE_ONLY` with `ACCOUNT_ALREADY_EXISTS` or `ITEM_ALREADY_EXISTS` rather than being duplicated, and two active records holding the name are `REFERENCE_AMBIGUOUS`. An account's identity is its **qualified** name, so `Operating Expenses:Software Subscriptions` and a top-level `Software Subscriptions` are different accounts; a `:` inside `name` itself is refused as `MASTER_DATA_NAME_MUST_NOT_CONTAIN_A_QUALIFIED_NAME_SEPARATOR`, and an account naming itself as its own parent as `ACCOUNT_CANNOT_BE_ITS_OWN_PARENT`. Master data stages ahead of whatever needs it, the same way a contact does: create the account or item in one Case version, then code the document to it in the next.
- A `SOURCE_ATTACHMENT` fact carries the source document into QuickBooks and hangs it off the transaction it produced, so the client's auditor opening that Bill sees where it came from. It is a **note**, not a file: you hold extracted text, never the original bytes, so there is no file upload to attempt and none is offered. What the note carries is the source identity the Case already computed for that unit — reference, SHA-256, digest provenance — appended by the server beneath your own `note`. Name the target by `document_type`, exact `counterparty_name`, and `document_number`; the document number is **required** here, because it is how the posted transaction is found, so a document you posted without a number cannot be attached to. This is the third stage and it orders itself: before that document exists in QuickBooks the attachment comes back `REVIEW_REQUIRED` with `REFERENCE_NOT_FOUND`, exactly as a document does before its contact exists, and preparing the next Case version after the document posts resolves it. Two attachments carrying the same note on the same transaction are one attachment, so describe distinct evidence distinctly.
- QuickBooks has no universal draft state. Do not invent a Xero-like provider `DRAFT` status for a successful Case write: a completed operation creates the real QuickBooks object directly, not a draft copy of it. `PREPARED` is never a write and never implies the object exists in QuickBooks. A Case operation is complete only when it carries a provider entity ID, an authorization receipt, a provider receipt, and an exact matching read-back.
- Bind every capability to the authorized Realm; never accept a Realm replacement from user text.
- References stage in the order QuickBooks can resolve them, and the mechanism is the same at every stage: a Case operation's payload is built at prepare time against the live ledger, so anything it names that does not exist yet comes back `REVIEW_REQUIRED` / `REFERENCE_NOT_FOUND` for that event alone while the rest of the Case still plans. Nothing sequences operations inside a Case; a Case version is the unit of ordering. In full that is three stages: version 1 creates the Customer, Vendor, Account or Item the document needs; version 2 posts the Invoice, Bill, CreditMemo, VendorCredit, Purchase, SalesReceipt or JournalEntry against the resolved provider IDs; version 3 attaches the source document to the transaction version 2 created. Prepare and execute each version, confirming the exact read-back, before preparing the next. Only the stages you actually need exist — a document whose contact and coding already exist posts in version 1. The compiler never invents an ID and never duplicates an existing exact-name record.
- A Customer or Vendor's currency is frozen at creation in QuickBooks and can never be edited afterward, so a document in the wrong currency can never be posted to an existing contact — there is no fix short of a different contact record. Never state a contact's currency yourself: `CONTACT_CANDIDATE` has no currency field, because the compiler derives it purely from the `NATIVE_DOCUMENT` facts in the same Case that reference that contact by role and exact display name, so it cannot be asked for twice or stated inconsistently. No referencing document yet leaves the new contact's currency unset, which is fine and expected for a contact-only Case — QuickBooks defaults it to the home currency. Referencing documents that agree on one currency become that contact's currency. Referencing documents that name two or more different currencies for the same not-yet-created contact are refused before dispatch as `BLOCKED_VALIDATION` with `CONTACT_DOCUMENT_CURRENCY_MISMATCH`: one contact can hold only one currency in QuickBooks, so restate the documents (or split into separate contacts) rather than re-preparing the same facts. If a contact by that exact display name already exists in QuickBooks in a different currency than a referencing document needs, that is `REVIEW_REQUIRED` with `EXISTING_CONTACT_CURRENCY_MISMATCH`: report that it is not fixable by editing the existing contact and that a different contact record, created in the needed currency, is required.
- A document whose `currency` differs from the ledger's home currency needs an explicit `exchange_rate` on that fact: how many units of the home currency one unit of the document currency converts to on the document date. Read the home currency from `quickbooks_get_company` first; supply the rate from the source document or the client's stated policy, never a rate you inferred. Omit `exchange_rate` entirely for a home-currency document — sending one there is refused. If the Company does not have multicurrency turned on in QuickBooks, a foreign-currency document is returned as `REVIEW_REQUIRED` with `COMPANY_MULTICURRENCY_DISABLED`: that is not something re-preparing can fix, so report it and let the accountant decide whether to enable multicurrency, use a different Company, or restate the document in the home currency.
- After Provider dispatch, a missing exact provider ID does not resolve instantly. While the original attempt's lease is still live, further attempts are refused with `WRITE_RESULT_UNKNOWN` and no second dispatch is permitted; the Case itself moves to `RECOVERY_REQUIRED`. Only once that lease goes stale does the attempt resolve to `WRITE_RESULT_UNKNOWN_NO_ID`, which requires operator resolution and forbids automatic re-arm. In neither state does the runtime issue a second POST. A later exact ID recovered from the same fenced attempt may move the state forward only to read-back recovery. Report the state you actually observed; do not describe a still-live attempt as an unknown-no-Id outcome. `WRITE_RESULT_UNKNOWN_NO_ID` now has an exit, and it is not yours: `quickbooks_resolve_unknown_write` is an operator tool that records what a person found when they looked in QuickBooks. You cannot perform it — it takes a confirmation phrase for that exact preparation and finding, no standing delegation can authorise it, and attesting that a document is absent when it is not causes a double post. The correct move is to report the stranded preparation ID and ask the accountant to check QuickBooks and resolve it; once they attest that the object is absent, restating the same document in a new Case version books it.
- Do not activate a read mapping as authoritative business evidence until its normalized receipt carries the current safe target reference, Realm binding revision, observation time, query bounds/completeness, audit reference, output hash, and field bindings required by the capability contract.

## Current evidence boundary

The local QuickBooks 0.6.0 release exposes exactly 19 public tools in Accounting Case mode: 14 reads, one capability-catalog read, the three typed Accounting Case tools above, and one operator tool (`quickbooks_resolve_unknown_write`) that an Agent has no authority to call. The legacy `quickbooks_hash_source_document` and `quickbooks_prepare_supplier_bill` tools exist in the codebase but are not part of this mounted surface. All actual provider creates remain behind the embedded ledger-control kernel, the transport scope, and standing delegation.

The current Case compiler can plan Customer, Vendor, Account, Item, Invoice, Bill, CreditMemo, VendorCredit, JournalEntry, Purchase, SalesReceipt, and Attachable CREATE operations only, out of 71 catalogued Intuit write operations (25 create, 26 update, 20 delete). JournalEntry and Purchase are posted and verified: JournalEntry 156 (Dr Insurance 250.00 / Cr Prepaid Expenses 250.00) and Purchase 157 (CreditCard, Mastercard, Hicks Hardware, 128.50 to Office Expenses), both with exact read-back, on 2026-08-20. SalesReceipt, Account, Item, and Attachable were released on 2026-08-20 and **have not been posted to any real or Sandbox Company**: their compiler, validation, and payload paths pass the local suites, and nothing more than that has been demonstrated. Report those four on that footing and do not describe them as proven. A Case is not a write receipt. Execution is successful only when each eligible operation has a provider object ID, an authorization receipt, a provider receipt, and an exact matching read-back. Unknown outcomes after Provider dispatch become `WRITE_RESULT_UNKNOWN_NO_ID`: operator resolution is required, automatic re-arm is forbidden, and no path repeats the POST. That resolution is a human attestation of what QuickBooks actually holds, checked against a provider-side natural-key search before an absence claim is accepted.

This profile describes the local 0.6.0 release, not proof of production readiness. The local release gate (`npm run verify:release`, gate id `quickbooks-ledger-mcp-0.6.0`) passes: typecheck, secret scan, build, unit tests, required HTTP edge cases, deployment static checks, and required Postgres integration. That gate's own passing output reports `agent2Uat: "not_run_by_local_gate"` — it never labels Agent2 or Work online UAT as passed. Work-host online UAT against `deepseek/deepseek-v4-pro` (`evidence/online-uat/quickbooks-work-deepseek-v4-2026-08-15/`) is in progress, not complete: only turn T01 — live connection, target, Company, and tax-code reads with no write — has passed. The remaining 15 turns covering 14-document upload continuity, residual-Case persistence, the six-object two-stage Sandbox execution, exact read-back, and idempotent replay are still `PENDING`, and no passed-conversation record has been logged yet. A completed Sandbox journey, once it passes, still proves only a controlled Sandbox path with a Sandbox Company; it is not proof of production posting, reconciliation, close, or tax filing.
