# QuickBooks Ledger MCP — 验收要求重构（2026-08-19）

本文替换此前"逐条功能打勾"式的验收清单。写它的直接原因是：清单上最后一条
（外币单据落账）被标为"代码路径已就绪"，而实跑之后它不但没通过，还带出了三个
此前从未被任何验收条目覆盖的缺陷。

## 为什么要重构

把最近两轮所有阻塞发布的缺陷按类归一下：

| 缺陷 | 类别 |
| --- | --- |
| 8 月 15 日的 Case 因准备件过期永久卡死 | 可恢复性 |
| 外币拒绝给出的补救手段在系统里不存在 | 诚实拒绝 |
| 重挂载资格读的是可变的 `error_receipt` | 可恢复性 |
| dispatch 之后的拒绝把单据永久锁死 | 可恢复性 |
| `WRITE_RESULT_UNKNOWN_NO_ID` 没有任何人工处置出口 | 可恢复性 |

五条，五条都是**失败语义**缺陷，零条是正常路径缺陷。

而此前的验收条目**全部是正常路径**。这不是巧合：这套连接器的工程投入几乎全在
持久化写入生命周期上——租约围栏、dispatch 标记、内容哈希幂等、触发器不变量。
只测正常路径，等于只测这套系统投入最少的那一部分。

外币那一条尤其能说明问题：它指向了一个正确的测试，但理由是错的。它想验的是
"SGD 能不能入账"，而它实际撞出来的 bug 与币种毫无关系——任何 provider 侧拒绝
都会把单据永久锁死。**如果 SGD 那天碰巧成功了，我们会带着这个 bug 发布。**

## 重构后的验收要求

连接器真正的对外声明不是"能建 6 类对象"，而是：

> 一个 agent 能对真实账套推进真实的会计工作，每一个结果要么正确，要么可恢复，
> 且不会静默重复入账。

拆成四条可证伪的属性。每一条的证据都必须来自**服务端审计或 provider 侧读回**，
agent 的自述一律不作数——这一条是硬性的，本轮就发生过 agent 把"我入不了账"
归因为环境问题，而真实原因是代码缺陷。

### P1 忠实性

落到账本里的对象与来源单据逐字段一致。

状态：**已通过。** 6 个已发布能力各有真实 QuickBooks 对象，同 id 精确回读。

### P2 恰好一次

provider 写入计数只移动预期的笔数，且这一性质在重试、失败、恢复之后仍然成立。

状态：**已验证但取证方式不合格。** 每次都是我手工查库比对。应当成为运行中的
断言，而不是事后人工核对。

### P3 可恢复性

每一种失败都让会计能够据以行动。这是新增的主闸，也是上表里五条缺陷全部所在的地方。

按系统自己已经区分的 `failureLayer` 取值列举，不新增分类机制：

| 失败层 | 触发方式 | 通过标准 |
| --- | --- | --- |
| `DETERMINISTIC_VALIDATION` | 错误税码、单据不平 | agent 能据错误自行改正并重提 |
| `PROVIDER_REFERENCE` | 同名联系人多条 / 引用不存在 | 指名到具体字段，会计能消歧 |
| `PROVIDER_CONFIGURATION` | 账套未开多币种 | 拒绝，且补救手段真实可达（见 P4） |
| **provider 侧明确拒绝（dispatch 之后）** | 联系人币种与单据不符、单号重复 | **改正后同一单据能重新入账** |
| **结果真正未知** | 5xx / 超时 | 不得自动重挂载，且必须存在人工处置出口 |
| `CONCURRENCY_OR_VERSION` | 同 Case 并发执行 | 指出应当复用的 request id |
| 准备件过期 | 隔夜恢复 | 重新授权后可继续 |

加粗两行是本轮的重点：第一行此前是坏的，第二行此前**根本没有出口**。

### P4 诚实拒绝

拒绝时给出的补救手段，必须是 agent 用它手上真实拥有的工具能够达成的。

反例已经出现过一次：外币单据被拒，理由是"尚未提供准确的汇率策略"，而 intake
里当时根本没有任何字段能提供汇率。照它说的做也永远做不到。该缺陷已单独修复，
但作为一类性质此前从未被验收覆盖。

## 与三状态设计的关系

持久化写入生命周期要回答的问题只有一个：**QuickBooks 里是否可能存在一个我们
没有 id 的对象？** 这个问题只有三个答案：

1. **确认已写入** —— 手上有精确 id → 落盘、回读、终态
2. **确认未写入** —— provider 完成了一次响应并拒绝 → 可改正、可重试
3. **未知** —— 没有完成的响应，或响应无法解释 → 不得自动重挂载

原实现只有 1 和 3，状态 2 塌陷进了 3，这是单据被永久锁死的全部原因。

但补上状态 2 之后，设计仍然不完整：**状态 3 没有任何转出边。** 修完之后真正的
未知会变得罕见，但不会消失（Intuit 5xx、网络分区），而一旦发生，那张发票依然
永久入不了账。一个可达却无出口的状态，正是我在批评原设计时指出的同一种不完整。

状态 3 的正确出口不是自动化——真正的未知本来就需要人去 QuickBooks 里看一眼再
判断。所以出口是**人工判定存证**：一个工具，让操作者记录他查到的事实（"查过了，
不存在" / "查过了，id 是 N"），系统据此写收据并转移状态。是一张收据加一次状态
转移，不是工作流引擎。

补上之后，三个状态各自都有出口，设计才闭合。

## 状态 2 与状态 3 的共同出口：换代（supersession）

补状态 2 的时候撞上了一个结构性事实，它决定了整个设计的形状。

**已 dispatch 的准备件永远不能被复用。** 迁移 033 的 shape 约束要求
`state IN ('PREPARED','REJECTED')` 时 `dispatch_started_at IS NULL`，而同一迁移的
触发器又规定 `dispatch_started_at` 一经写入不可变、租约在 dispatch 之后不可移动。
两条合起来：dispatched 的行回不到 `PREPARED`。这是对的，不要动它。

**而"改单据换个哈希"这条退路不存在。** 带单号的单据，其
`stableOperationKey` 只由 `documentType + counterpartyName + documentNumber` 推导，
金额、日期、币种、行项目**被刻意排除**。这对幂等是正确的——同一供应商的同一张
发票号就是同一张单，无论 agent 换什么措辞重述它。但它同时意味着：**修好环境问题
从不改变这个键。** 补币种表、重连过期 token、补授权 scope、为同一供应商另建一个
SGD 供应商档——键完全不变，拿回来的还是那行被污染的准备件。

所以「可证明未写入」要真正可用，只能靠**在同一个逻辑操作上开启新的一代**，
且只在非写入被确立之后才允许。

非写入的确立有两个来源，而它们通向同一个出口：

| 来源 | 触发 | 是否需要人 |
| --- | --- | --- |
| provider 证据 | Intuit 完成响应并以 Fault 拒绝（400/401/403/404） | 否，自动 |
| 操作者存证 | 人去 QuickBooks 查过，记录"不存在" | 是 |

对称地，如果操作者查到的是"在，id 是 N"，那就不是换代——该行采纳这个 id，
走回读校验，写入本来就成功了。

于是三个状态各自闭合：

1. **确认已写入** → 落盘、回读、终态
2. **确认未写入** → 换代、可重试
3. **未知** → 操作者存证把它转成 1 或 2

这是**一个**机制两种证据来源，不是两套东西。落地代价：一个"代"的概念、
一个存证工具、一个迁移（038）。被污染的旧准备件行保留不动，作为审计证据。

需要窄口放开两处不可变约束，做法沿用 036 的先例——只在证据成立时放行，
且只允许那一个方向：
- Case 操作的 `preparation_id`（037 中一经写入不可变）在换代时可指向新准备件；
- 037 的重挂载谓词增加第二个分支，接纳"已 dispatch 但可证明未写入"的准备件
  （`provider_entity_id IS NULL`、`provider_outcome_receipt IS NULL`、
  `execution_attempt_state='RESOLVED_NO_WRITE'`、收据断言
  `providerMutationPossible: false`）。

`client_request_id` 由内容键加代号推导。同一代内幂等性完全不变；开启新一代的
唯一途径是上面那个被证据把守的分支。**双重入账的防线没有被削弱：能被换代的行，
是那些有证据证明它从未写入的行。**

## P5 覆盖：记账所需的动作要齐

前四条属性问的是「做的事对不对」。这一条问「该做的事做不做得了」，是 2026-08-20
新增的，因为验收到那天为止只覆盖了 6 个已释放动作，而一个会计根本无法用它结完一个月。

### 范围边界：不动钱

写能力表已经按 `providerEffect` 给全部 71 个动作分了类，边界直接用它，不另起一套：

| 归类 | 数量 | 在不在范围内 |
| --- | --- | --- |
| `CASH_MOVEMENT` | 10 | **不在**。Payment、BillPayment、Deposit、Transfer、RefundReceipt |
| `POSTING_TRANSACTION` | 12 | 在 |
| `LEDGER_ADJUSTMENT` | 2 | 在。JournalEntry |
| `ATTACHMENT` | 2 | 在 |
| `MASTER_DATA` | 19 | 在 |
| `NON_POSTING` | 6 | 在，但优先级低 |
| `DEACTIVATION` / `VOID_OR_PERMANENT_DELETE` / `PERMANENT_DELETE` | 20 | 在，风险最高，最后做 |

发起付款、转账、退款这类**动钱**的动作刻意不做。它们已经在
`QUICKBOOKS_UNSUPPORTED_EVENT_TYPES` 里作为残差事件被如实记录，而不是被静默丢弃——
这本身就是 P4 诚实拒绝的一部分。

`Purchase`（现金/支票/信用卡支出）在边界上，判定为**在范围内**：它记录的是钱已经出去
这件事（从银行对账单或收据补记），不是发起付款，写能力表也把它归在
`POSTING_TRANSACTION`。这是一次判断，不是默认，随时可以推翻。

### 通过标准

不是「71 个都释放」，而是：**一个会计能用它把一个月的账记完，不需要中途切回
QuickBooks 界面手工补。** 按此判断的必需项：

1. `JournalEntry` —— 计提、调整、重分类。缺它就没有月结。
2. `Purchase` —— 费用记录，交易量最大的一类。
3. `Attachable` —— 原始单据挂到交易上。产品前提是「从单据到账本」，
   而现在单据没跟着进去，客户的审计师在账套里看不到来源。
4. `Account` / `Item` —— 主数据，记账过程中必然要新增科目和商品。
5. `SalesReceipt` —— 现销。
6. 六类单据的 UPDATE —— 更正。会计改错记的分录是日常，不是例外。

每一项都必须走既有的 Case → prepare → execute 通路，继承持久化准备件、执行围栏、
三态写入结论、换代、精确回读。**任何一项另开一条写入路径都算不通过**——上一个版本
就是这么长出第二套生命周期的，后来净删了 2,971 行才拆掉。

## 收尾验收怎么跑

不新建故障注入装置。P3 的七行用现有测试套件系统性覆盖即可（现有测试已有内存
仓储与 provider 替身），**再加一次真实账套上的端到端恢复跑**。

那次真实跑的用例已经现成了：MBC-2026-0820 这张 SGD 发票目前正卡在
`WRITE_RESULT_UNKNOWN_NO_ID`，而它的地面真相我已经人工确认过（QuickBooks 界面
逐条核对，账单不存在）。它同时是被卡死的那张单和验收所需的那张单。

顺序：

1. 修复上线。
2. 用新的人工判定存证工具处置两行卡住的 SGD 准备件，据实存证"查过，不存在"。
   —— 这同时是该工具的第一次真实使用，且它处置的是一行地面真相已经独立确认过的行。
3. Agent 重试 MBC-2026-0820。预期得到一个 **dispatch 之前**的校验错误：
   供应商 63 是 USD，联系人币种建档即锁死，需要另建一个 SGD 供应商。
4. Agent 据此另建 SGD 供应商并入账。
5. 核验：provider 写入计数只 +2，账单与来源单据逐字段一致。

这一条链路一次性覆盖四条属性：dispatch 之后拒绝的可恢复性（P3）、联系人币种
推导（本轮 C）、拒绝给出的补救手段真实可达（P4）、外币入账本身（原目标），
以及写入计数恰好移动（P2）。

## 取证纪律

- 所有断言取自服务端审计表、准备件持久化行、或 provider 侧精确读回。
- agent 的自述不作为证据。
- "代码路径已就绪"不作为通过依据——本文档的存在就是因为这句话出过错。
  未实跑的一律记为未验证。
